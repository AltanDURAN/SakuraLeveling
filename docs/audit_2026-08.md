# Audit complet — SakuraLeveling (août 2026)

Périmètre : code (4 couches), bot Discord, webapp admin, UX joueur & admin,
tests, sécurité, performance, dette technique.
Méthode : analyse statique du dépôt, exécution de la suite de tests, navigation
réelle de l'admin (Playwright + captures des 19 pages), revue des patterns.

**Volumétrie** : 302 fichiers Python, ~40 000 lignes (dont 12 300 de tests),
39 templates, 19 cogs, 15 routers admin, 493 tests (100 % au vert).

---

## 1. Ce qui est solide (à préserver)

| Point | Constat |
|---|---|
| **Architecture en couches** | **Zéro violation** : `domain` n'importe jamais `infrastructure`/`application`/`bot` ; `application` n'importe pas `bot` ; `infrastructure` n'importe ni `bot` ni `application`. C'est rare et précieux. |
| **Sécurité** | Tous les routers admin passent par `require_admin` (seul `auth_router` est ouvert, c'est le login). Aucun secret en dur dans les fichiers suivis. `.env` gitignoré. `assert_safe_admin_secret()` bloque le démarrage sur secret par défaut. 100 % ORM (aucune concaténation SQL). CSRF par vérification d'origine. |
| **Tests** | 493 tests verts, dont 261 domaine et 219 infrastructure. Un seul service domaine sans test (`adventurers_guild`, placeholder de 3 lignes). |
| **Filet d'erreur bot** | `@bot.tree.error` global : le joueur ne voit jamais d'erreur opaque, la stack part dans les logs. |
| **Mutualisation** | `BetaChannelOnlyMixin` (13/19 cogs), `resolve_player_stats`, `resolve_title_bonuses`, `_shared.py` admin, `json_writer.atomic_write_json` centralisé (+ git push automatique). |
| **Concurrence SQLite** | WAL + `busy_timeout` + rollback explicite : 3 process peuvent écrire sans « database is locked ». |
| **Index DB** | 76 index, colonnes chaudes couvertes (`player_id`, `code`, `status`, `expires_at`…). |

## 2. Risque n°1 — divergence `main` / `beta` (à traiter en priorité)

**Constat mesuré** : `beta` a **370 commits absents de `main`**, dont ~250 commits
`admin: contenu … mis à jour` générés par l'auto-push de l'admin web.

Contenu présent **uniquement sur beta** :

| Fichier | Écart |
|---|---|
| `mob_placements.json` | +543 lignes |
| `items.json` | +199 lignes |
| `mobs.json` | +138 lignes |
| `family_drops.json` | +114 lignes |
| `mob_element_weights.json` | +96 lignes |
| `farm_zones.json` | +58 lignes |
| **20 fichiers d'assets** | 14 images de mobs (tous les démons + morts-vivants) et 6 décors |

**Conséquences concrètes**
1. En local (`main`), le bot affiche des carrés gris et la webapp renvoie des 404
   sur `/assets/mobs/*.png` — c'est reproduit et vérifié dans cet audit.
2. Un reseed ou un redéploiement depuis `main` **détruirait** tout le contenu créé
   depuis l'admin.
3. Le workflow documenté (« dev sur main → merge vers beta ») est en réalité
   **bidirectionnel non réconcilié** : le contenu ne remonte jamais.

**Correction recommandée** (à valider) :
```bash
git checkout main && git merge origin/beta   # rapatrie contenu + assets
git push origin main
```
Puis **rituel** : rapatrier `beta → main` après chaque session d'édition admin.
Alternative structurelle : faire pousser `git_sync` sur `main` et laisser le
déploiement faire `main → beta` (sens unique, plus sain).

## 4. Dette technique identifiée (non corrigée — décision à prendre)

### 4.1 Sous-système de quêtes « legacy » entièrement mort
`quests.json` (22 entrées) est **seedé à chaque déploiement** dans les tables
`quest_definitions` / `player_quest_states`, mais **aucun use case ni cog ne les
lit** : les quêtes réelles sont `daily_quests.json` et `weekly_quests.json`
(systèmes séparés et vivants).

- `app/domain/services/quest_service.py` : **zéro référence dans tout le dépôt**.
- `QuestRepository` : utilisé uniquement par le seeder.

→ Soit supprimer (service + seeder + JSON + tables via migration), soit
documenter explicitement comme « réservé pour la refonte des quêtes », comme
c'est déjà fait pour `GatherResourceUseCase` (`/gather` retiré volontairement).

### 4.2 Autres reliquats
- `ClaimWeeklyQuestUseCase` : remplacé par `ClaimAllWeeklyUseCase`, n'est plus
  utilisé que par ses propres tests.
- `HelpSubscriberRepository` + table : `/chad` utilise désormais un rôle Discord ;
  ne subsiste que pour la purge de `reset_player` et ses tests.

### 4.3 Fichiers hypertrophiés
`player_cog.py` (1 787 l., 27 commandes) et `content_router.py` (1 747 l., 42 routes)
concentrent trop de responsabilités. Découpage suggéré, sans urgence :
`player_cog` → *profil/consultation*, *équipement*, *craft/forge*, *sets* ;
`content_router` → un router par entité (le reste de l'admin le fait déjà).

## 5. Scalabilité — le point à surveiller

**N+1 sur le leaderboard.** `GetLeaderboardUseCase` boucle sur **tous** les
joueurs et appelle `resolve_player_stats` pour chacun ; or ce helper émet à lui
seul ~5 requêtes (allocations d'arbre, titres, effets temporaires, niveaux de
forge, équipement).

- Aujourd'hui (2 joueurs) : imperceptible.
- À 200 joueurs : **~1 000 requêtes** par `/classement`, plus le recalcul complet
  des stats en Python — plusieurs secondes, et ça bloque un worker.

Pistes, par ordre de coût croissant : (a) charger en lot (une requête par table,
regroupée en dictionnaires) ; (b) mettre en cache le power score quelques minutes ;
(c) le persister et le recalculer sur événement (level-up, équipement, forge).

**Autre point** : les repositories committent eux-mêmes (28 fichiers) — la
frontière transactionnelle appartient donc au repo, pas au use case. C'est assumé
et compensé par le rollback de `get_db_session`, mais ça empêche toute opération
multi-repos réellement atomique. À ne pas généraliser aux nouveaux repos (les
repos récents — événements, effets, niveaux d'item — utilisent `flush()` +
commit par l'appelant, c'est le bon modèle).

## 6. UX / UI

### 6.1 Admin web — homogénéisation
Le style global (Sakura pastel, dark mode, nav groupée, cartes) est **cohérent
sur les 19 pages**. Restent des écarts de *patterns*, pas de style :

| Écart | Détail | Reco |
|---|---|---|
| Affordance « créer » | Carte « + Nouvel objet » **dans la grille** (items, mobs) vs **bouton en haut à droite** (crafts, zones) | Choisir le bouton haut-droite partout (visible sans scroll, ne se confond pas avec une donnée) |
| Liste : cartes vs tableau | Cartes (items, mobs, joueurs) vs tableau (événements, zones, titres, shop) | Garder les deux, mais par **règle explicite** : carte si l'entité a une image, tableau sinon |
| Aperçu d'image | `/admin/events` affiche `chest.png` en **texte** alors que mobs/items affichent la vignette | Afficher la vignette |
| Message « restart bot » | Présent sur zones et événements, absent ailleurs alors que la règle est la même (caches module-level) | Bandeau standardisé sur toutes les pages de contenu lu par le bot |

### 6.2 Bot — cohérence des commandes
- Renommage FR globalement **fait** (`profil`, `inventaire`, `classement`…).
- **Reste en anglais** : les sous-commandes de `/brocante` — `list`, `my`, `sell`,
  `buy`, `cancel` — alors que c'est une commande **joueur**. À franciser
  (`annonces`, `mes_annonces`, `vendre`, `acheter`, `annuler`).
  (`daily`, `help`, `ping`, `cd` sont volontairement inchangées.)
- `defer()` : correctement posé sur les commandes lourdes ; les cogs sans `defer`
  ont été vérifiés un par un — leurs commandes sont légères (aucun rendu Pillow),
  sauf le cas `/recettes` corrigé ci-dessus.

### 6.3 Documentation
`CLAUDE.md` décrit un `interaction_check` **par cog** ; la réalité est un
**mixin partagé** (`BetaChannelOnlyMixin`) — meilleure implémentation, mais la
doc doit être mise à jour. Idem : le tableau des commandes cite encore
`/admin spawn_event`, devenu `/event spawn`.
